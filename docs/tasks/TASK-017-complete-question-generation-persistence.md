# 4. Persistence Workflow

The completed workflow should conceptually be:

```text
User selects generation configuration
        │
        ▼
Build generation context
        │
        ▼
Generate questions using AI
        │
        ▼
Validate AI response
        │
        ▼
Map AI response to persistence/domain model
        │
        ▼
Persist complete generation
        │
        ├── GenerationContext
        ├── Selected QuestionTypes
        ├── Selected QuestionPatterns
        └── GeneratedQuestions
        │
        ▼
Return generated questions to the UI
```

The existing question-generation behavior must continue to work.

Persistence should be added without unnecessarily changing the UI behavior.

# 5. Repository / Persistence Layer

Create or extend the project's existing repository/data-access architecture.

Do NOT introduce a second competing database-access pattern.

The persistence layer should provide a clean abstraction for saving a complete generation.

The exact API should follow the existing project architecture, but conceptually it should support:

```text
Create GenerationContext
Save selected QuestionTypes
Save selected QuestionPatterns
Save GeneratedQuestions
```

Prefer a single high-level operation for the complete generation, for example:

```text
saveGeneration(...)
```

rather than making the UI responsible for orchestrating individual database writes.

The repository must not expose Prisma-specific implementation details to unrelated application layers.

# 6. GenerationContext Persistence

When a generation is successfully persisted, create one `GenerationContexts` record containing:

- Name
- DifficultyLevel
- AIProvider
- AIModel
- Prompt
- CreatedAt

The `Id` is generated by PostgreSQL/Prisma.

## Generation name

The generation name must be unique.

Do not use a hard-coded name.

Generate a deterministic human-readable name based on the generation creation timestamp.

For example:

```text
Generation-2026-08-29-04-30-15
```

The exact formatting should follow the project's conventions, but it must:

- be unique enough for normal application usage
- be generated by the application
- not require user input
- be deterministic from the creation timestamp

If there is a better existing project convention, reuse it.

Persist every QuestionPattern selected by the user.

# 9. GeneratedQuestions Persistence

Every successfully generated AI question must be saved into:

```text
generated_questions
```

Map the existing AI response into the persistence model.

At minimum persist:

- GenerationContextId
- QuestionPatternId
- QuestionType
- QuestionNumber
- QuestionText
- ExpectedAnswer
- Explanation
- CreatedAt

The application must resolve the generated question's pattern to the correct existing `QuestionPatternId`.

The AI response's question-pattern label/name must not be stored as the database relationship value.

Use the existing selected QuestionPattern records to resolve the ID.

---

# 10. AI Response Mapping

Keep a clear separation between:

```text
AI Response
      ↓
Application/domain representation
      ↓
Persistence model
      ↓
PostgreSQL
```

Do not add database-specific fields such as:

- `GenerationContextId`
- `QuestionPatternId`
- database-generated `Id`
- `CreatedAt`

to the provider's response schema unless there is a strong architectural reason.

The mapper should enrich the AI response with the persistence information required by the database.

Pay particular attention to:

```text
AI question type
        ↓
QuestionType
```

and:

```text
AI question pattern name
        ↓
QuestionPatternId
```

---

# 11. Question Pattern Resolution

A generated question must be associated with an existing selected QuestionPattern.

The system must not blindly trust an AI-generated pattern name.

Use the selected QuestionPatterns from the current generation context to resolve the database ID.

If the AI returns a pattern that does not correspond to a selected pattern:

- do not save an invalid GeneratedQuestion
- fail the generation/persistence operation safely
- provide a useful error
- ensure the database transaction is rolled back

Do not silently assign an arbitrary pattern.

---

# 12. Transaction / Atomicity

The complete persistence operation must be atomic.

Use a database transaction.

Conceptually:

```text
BEGIN TRANSACTION

Create GenerationContext

Save selected QuestionTypes

Save selected QuestionPatterns

Save GeneratedQuestions

COMMIT
```

If any step fails:

```text
ROLLBACK
```

We must never leave a partially persisted generation.

For example, this state must not remain:

```text
GenerationContext       ✅
QuestionTypes           ✅
QuestionPatterns        ✅
GeneratedQuestion 1     ✅
GeneratedQuestion 2     ❌
GeneratedQuestion 3     not saved
```

Instead, the entire operation should roll back.

---

# 13. Failure Handling

Consider failures from:

- AI response validation
- Question pattern resolution
- Invalid QuestionType
- Invalid DifficultyLevel
- Database constraint violations
- Prisma errors
- Unexpected repository errors

Do not swallow errors.

Use the project's existing error-handling conventions.

The UI should receive an appropriate failure response rather than displaying a successful generation when persistence failed.

---

# 14. Ordering of Operations

The preferred flow is:

```text
1. Validate user configuration
2. Generate AI questions
3. Validate AI response
4. Resolve QuestionPatterns
5. Begin database transaction
6. Create GenerationContext
7. Save selected QuestionTypes
8. Save selected QuestionPatterns
9. Save GeneratedQuestions
10. Commit transaction
11. Return questions to UI
```

Do not create database records for an AI generation that failed validation.

Ideally, database persistence should happen only after the AI response is valid enough to persist.
