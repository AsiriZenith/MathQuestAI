# Lesson 3 — Database Design & Prisma (including transactions)

Goal of this lesson: read the real schema, understand why it's shaped the way it is, and see how Prisma is wired into this specific project (the driver-adapter setup, the client singleton, and — since no current code path needs one — where a transaction *would* go if a feature here required one). Lesson 4 picks up from here and shows how this schema gets queried into the shapes the rest of the app consumes; this lesson is only about the schema and the client, not the query functions built on top of it.

## 1. The schema, read top to bottom

`prisma/schema.prisma` defines six models. Read together with `docs/project-management/database.md`, they form one hierarchy plus two tables hanging off its bottom node:

```
Subject → Topic → Subtopic → QuestionPattern → { ReferenceQuestion, QuestionGenerationRequest }
```

```prisma
model Subject {
  id        String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  name      String   @db.VarChar(100)
  language  String   @db.VarChar(50)
  ...
  topics    Topic[]

  @@unique([name, language], map: "uq_subject_name_language")
  @@map("subjects")
}

model Topic {
  id        String    @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  subjectId String    @map("subject_id") @db.Uuid
  name      String    @db.VarChar(100)
  ...
  subject   Subject   @relation(fields: [subjectId], references: [id], onDelete: NoAction, onUpdate: NoAction, map: "fk_topics_subject")
  subtopics Subtopic[]

  @@unique([subjectId, name], map: "uq_topic_subject_name")
  @@map("topics")
}
```

`Subtopic` and `QuestionPattern` continue the same pattern one level deeper — each has a foreign key up to its parent, a child collection down, and a `@@unique` compound constraint scoping name-uniqueness to the parent (a subtopic name only has to be unique *within its topic*, not globally).

A few Prisma/PostgreSQL conventions worth naming explicitly, since you'll see them on every model:

- **`@map` / `@@map`** — the physical PostgreSQL table is `subjects` (snake_case), but Prisma Client gives you `prisma.subject` (PascalCase singular model, camelCase fields) in TypeScript. `@map("subject_id")` and `@@map("subjects")` are what make that translation happen without touching the real column/table names. `database.md` §29 states the principle behind this directly: *"the existing PostgreSQL schema is the source of truth... if Prisma introduces naming differences... use explicit mappings rather than changing the PostgreSQL schema."* The database came first; Prisma's naming conventions were layered on top of it, not the other way around.
- **`@default(dbgenerated("gen_random_uuid()"))`** — every primary key is a UUID generated by Postgres itself (the `gen_random_uuid()` function), not by Prisma or application code. `dbgenerated(...)` tells Prisma "don't try to compute this default yourself, just know the database will fill it in."
- **`onDelete: NoAction, onUpdate: NoAction`** on every relation — deleting a `Subject` will not cascade and silently wipe its `Topic`s; the database will reject the delete instead. For a hand-seeded educational hierarchy that's edited rarely and deliberately, refusing accidental cascading deletes is the safer default.

### The two tables at the bottom: `ReferenceQuestion` and `QuestionGenerationRequest`

```prisma
model ReferenceQuestion {
  id                String          @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  questionPatternId String          @map("question_pattern_id") @db.Uuid
  difficultyLevel   String          @map("difficulty_level") @db.VarChar(20)
  questionText      String          @map("question_text")
  expectedAnswer    String          @map("expected_answer")
  explanation       String?
  ...
}

model QuestionGenerationRequest {
  id                String          @id @db.Uuid
  questionPatternId String          @map("question_pattern_id") @db.Uuid
  difficultyLevel   String          @map("difficulty_level") @db.VarChar(20)
  generationPrompt  String          @map("generation_prompt")
  ...

  @@unique([questionPatternId, difficultyLevel], map: "uq_question_generation_requests_pattern_difficulty")
}
```

Neither of these has its own `Difficulty` table — `difficultyLevel` is just a `VARCHAR(20)` string (`"Easy"` / `"Medium"` / `"Hard"`) on each row. Difficulty isn't a lookup entity with its own identity in this schema; it's a **key**, always paired with a `questionPatternId`, that selects which reference examples and which generation instructions apply. That's why `QuestionGenerationRequest` has a compound unique constraint on `(questionPatternId, difficultyLevel)` rather than a difficulty foreign key: for a given pattern, there is exactly one generation-prompt row per difficulty level. `database.md` §10 states the reasoning directly — the same Question Pattern needs *different* reference questions and generation instructions per difficulty, so difficulty has to travel alongside the pattern at the row level, not live in its own table.

Also worth noticing what's deliberately **not** a column: `QuestionGenerationRequest` has no `questionCount`. `database.md` §13 calls this out explicitly — how many questions to generate is treated as a *common* instruction applied to every request, not a per-pattern/difficulty database property. That's a concrete instance of a broader principle this schema follows throughout: a Question Pattern's specific instructions live in the database, but instructions that apply universally (question count, output format, general phrasing rules) live in code, in the common-instructions layer covered in Lesson 6.

### What's deliberately absent from this schema

`database.md` §22 lists it outright: no `Students`, `Teachers`, `Teams`, auth, sessions, persisted generated questions, or evaluation history. You met the *reason* for this in Lesson 1 (`CLAUDE.md` §14 — scope stays narrow, no enterprise features without an explicit requirement); this schema is where that decision becomes concrete. Notice specifically: **generated questions themselves are never written back to the database.** The flow is `QuestionGenerationRequest → AI API → Generated Questions → Display → Evaluation`, entirely in memory for the lifetime of one browser session (Lesson 5 covers how). If you go looking for a `GeneratedQuestion` table expecting to find where a generation result gets persisted, it isn't there on purpose — `database.md` §33 lists it as a considered-but-not-implemented future possibility, not a gap.

### A concrete example of "the database is the source of truth"

`database.md` §5 has a short note worth reading as a case study, not just a schema detail:

> The actual `subjects` table also has a `language` column (`VARCHAR(50)`)... with a unique constraint on `(name, language)`. This was not previously documented here.

This was discovered by introspecting the real, already-existing Postgres database while wiring up Prisma (`docs/agent-feedbacks/TASK-004-configure-prisma-postgresql.md`) — the column existed in the live database but nowhere in the design docs. Per `database.md` §29's own rule ("the existing PostgreSQL schema is the source of truth"), the right move was to record the discrepancy in the docs, not to "fix" the database to match outdated documentation, and not to silently drop the column from the Prisma schema either. `Subject.language` in `prisma/schema.prisma` today exists because of that principle in action.

## 2. Prisma in this project — the v7 driver-adapter setup

`lib/prisma.ts`, in full:

```ts
import { PrismaClient } from "@/lib/generated/prisma/client";
import { PrismaPg } from "@prisma/adapter-pg";

const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient };

const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });

export const prisma = globalForPrisma.prisma ?? new PrismaClient({ adapter });

if (process.env.NODE_ENV !== "production") {
  globalForPrisma.prisma = prisma;
}
```

Two things to understand here, both project-specific rather than generic Prisma knowledge:

**The `PrismaPg` driver adapter.** This project uses Prisma 7 (`package.json`: `"prisma": "7.9.1"`), which requires an explicit driver adapter for connecting to a SQL database rather than Prisma's older built-in query engine binary. `PrismaPg` (from `@prisma/adapter-pg`) wraps the `pg` package and is what Prisma Client actually uses to talk to Postgres — it's constructed once from `DATABASE_URL` and passed into `new PrismaClient({ adapter })`. If you've used Prisma before this version, the built-in-engine model you remember doesn't apply here; this is the "not the Next.js you know"-style warning from `CLAUDE.md`, but for Prisma instead of Next.

**The `globalForPrisma` singleton guard.** In development, Next.js hot-reloads server modules on every file save, which would otherwise re-run `new PrismaClient({ adapter })` on every reload and leak a new database connection pool each time. Stashing the client on `globalThis` and reusing it if it already exists (`globalForPrisma.prisma ?? new PrismaClient(...)`) survives hot reloads; the `if (process.env.NODE_ENV !== "production")` guard means this caching-on-`globalThis` trick only happens in development — in production, module state doesn't get hot-reloaded away, so there's no reason to reach for `globalThis` there.

Every part of the app that touches the database — `lib/db/education.ts`, `lib/db/generation-context.ts`, and the `app/dev/db-check` route — imports this one `prisma` export rather than constructing its own client. One client instance, shared everywhere.

## 3. Transactions — the mechanism, and why nothing here uses one yet

Search the codebase for `$transaction` and you'll find nothing outside documentation and this lesson. That's not an oversight to fix — it's a direct consequence of the scope decision from section 1: this app has exactly one kind of write path that matters (none, really — it's a read-heavy context store), and zero code paths that need to perform *multiple dependent writes atomically*. A transaction only earns its place when a feature needs "these two-or-more writes must all succeed or all fail together." Nothing in this app currently writes twice.

That said, you should still know the mechanism, because a future feature might need it — `database.md` §33 floats `GeneratedQuestions`, `EvaluationResults`, and `ExperimentRuns` as future possibilities, and persisting any of those alongside a foreign key back to a `QuestionGenerationRequest` would be exactly the kind of multi-step write a transaction protects.

Prisma's `$transaction` comes in two forms:

**Sequential — an array of independent operations, all-or-nothing:**

```ts
const [subject, topic] = await prisma.$transaction([
  prisma.subject.create({ data: { name: "Mathematics", language: "English" } }),
  prisma.topic.create({ data: { name: "Algebra", subjectId } }),
]);
```

If either operation fails, both roll back — useful when you know all the operations up front and they don't depend on each other's results.

**Interactive — a callback that receives a transaction-scoped client (`tx`), for when later steps depend on earlier results:**

```ts
await prisma.$transaction(async (tx) => {
  const request = await tx.questionGenerationRequest.findUniqueOrThrow({
    where: { questionPatternId_difficultyLevel: { questionPatternId, difficultyLevel } },
  });

  await tx.generatedQuestion.create({
    data: { requestId: request.id, /* ... */ },
  });
});
```

If this app grew a feature to persist a generated question against its originating `QuestionGenerationRequest` — reading the request, then inserting a dependent row, and wanting both to succeed or fail together — this is the shape it would take: replace `prisma.foo` with `tx.foo` for each step inside the callback, and the whole block becomes one atomic unit. Until such a feature exists, there's nothing to point you at in this codebase beyond this explanation — that absence is itself the correct state of things per the project's scope.
